# C/C++ Coding Style for AI Agents

本文档从 `KYZG-OS.KSOS-018-V1.0 C&C++语言编码规范.docx` 提取并整理，用于约束 AI Agent 在本项目中生成、修改和审查 C/C++ 代码。若修改基于第三方开源项目，应优先遵循该开源项目既有规范；若项目已有更具体的本地规范，以本地规范为准。

## 基本原则

- 代码应保持质量、可读性、可维护性和一致性。
- 文件名、类名、变量名、函数名必须有明确语义，避免无意义缩写。
- 代码变更应尽量小而聚焦，不引入无关重构。
- 删除已经不用的代码，不保留注释掉的废弃实现。
- 避免绝对路径；受安装目录影响的路径应通过宏、静态常量或编译期生成的 `config.h` 管理。

## 格式化

- C/C++ 源码必须使用项目统一的 `.clang-format` 格式化。
- CMakeLists.txt 必须使用 `cmake-format` 默认格式。
- 缩进使用 4 个空格，禁止使用 Tab。
- `if`、`for`、`do`、`while`、`case`、`switch`、`default` 等语句独占一行。
- `if`、`for`、`do`、`while` 的执行体即使只有一行，也必须使用 `{}`。
- `case` 分支内的语句必须缩进，建议使用 `{}` 明确作用域。
- 一行只写一条语句，禁止把多个短语句写在同一行。
- 函数定义之间必须主动空行。
- `class`、`struct`、`union`、`enum` 定义之间必须空行。
- `.c`、`.cpp`、`.h`、`.hpp` 文件末尾必须保留空行。
- 较长语句必须拆行；长表达式优先在低优先级操作符处换行，并保持缩进清晰。
- 函数调用参数过长时，按参数拆行，不要在单个参数表达式中间随意换行。
- 建议每行代码保持在约 10 个单词左右，以便阅读。

## 命名规范

### C

- 结构体、联合、枚举类型名使用驼峰命名，例如 `EthInfo`。
- 变量使用小写加下划线，例如 `string_value`。
- 函数名使用小写加下划线，例如 `get_user_name`。
- 宏定义和枚举成员使用全大写加下划线，例如 `PATH_GDM_CUSTOM`。
- 文件名使用小写加横杠，并尽量与文件内核心类型一致，例如 `accounts-manager.h`。

### C++

- 若项目区分 GTK/QT 规范，应遵循对应规范；若项目既不是 GTK 也不是 QT，默认采用 QT 规范。
- 命名空间、类、结构体、联合、枚举类型使用驼峰命名。
- 局部变量、结构体成员、联合成员：
  - GTK：小写加下划线，例如 `user_name`。
  - QT：小驼峰，例如 `userName`。
- 类成员变量：
  - GTK：小写加下划线，并以 `_` 结尾，例如 `dbus_connect_id_`。
  - QT：以 `m_` 开头，后接小驼峰，例如 `m_dbusConnectID`。
- 宏定义和枚举成员使用全大写加下划线。
- `typedef` 和 `using` 定义的类型使用驼峰命名。
- 函数名：
  - GTK：小写加下划线。
  - QT：小驼峰。
- DBus、gRPC 等配置接口名统一使用驼峰命名。
- QT 信号使用“名词可选 + 动词被动语态”，槽函数使用常规函数命名。
- 禁止使用单字符变量名，`i`、`j`、`k` 仅允许作为局部循环变量。
- 函数名必须准确描述功能。执行操作的函数使用动宾词组；OOP 方法可只保留动词，因为对象名已表达名词。

## 注释规范

- 注释优先解释“为什么这样做”，不要重复描述代码“怎么做”。
- 对外提供的函数接口，包括 C++ 构造函数和公共成员函数，必须使用 Javadoc/Doxygen 风格注释说明：
  - 接口作用。
  - 参数含义、方向、是否允许为空。
  - 返回值含义、错误值、内存释放责任。
- 可使用的标签包括 `@brief`、`@param[in]`、`@param[out]`、`@param[in,out]`、`@return`、`@deprecated`、`@exception`、`@throws`、`@see`、`@since`、`@bug`。
- 对外提供的枚举和结构体必须提供注释；非对外类型建议提供注释。
- `class`、`struct`、`union`、`enum` 的重要成员建议添加注释；一目了然的成员可省略。
- 常量、`static` 变量、宏、`typedef` 在声明或定义时建议说明用途；局部且显而易见的常量可省略。
- 对当前实现存在的问题或待办事项，可使用：
  - `FIXME`：代码错误或不能工作，需要修复。
  - `TODO`：需要实现但尚未实现。
  - `XXX`：勉强可工作，但存在性能差等问题。
- 新增文件、新增函数或重大重构后，应按项目文件头规范更新作者署名。
- 禁止为了某次修复在代码中留下 `add by`、`modify by`、`delete by` 等变更历史；此类历史交给版本控制系统。

## 目录结构

推荐工程目录结构：

```text
include/          对外接口头文件或项目通用头文件
data/             配置文件和数据
doc/              文档
lib/              静态库和动态库相关代码
resources/        资源文件
resources/images/
resources/styles/
src/              源代码
test/             测试代码
translations/po/  翻译文件
```

## 构建与发布

- 项目构建应使用 CMake 或 Meson，推荐 CMake。
- CMake `project()` 必须定义项目版本号。
- 提供共享库或头文件接口的程序，应提供 `pkg-config` 的 `.pc` 文件定义 `cflags` 和 `ldflags`。
- 安装的共享库 `.so` 文件末尾应添加版本号，例如 `libkiranwidgets-qt5.so.2.1`。
- 共享库版本号应与项目版本号保持一致，并尽量保证不同版本之间接口兼容。

## 可读性与控制流

- 必须显式使用括号表达运算符优先级，避免依赖默认优先级。
- 禁止使用魔术数；有业务含义或物理含义的数字必须用有意义的常量、枚举或宏替代。
- 不要滥用 `goto`；除非确有必要，应使用结构化控制流。
- 函数缩进层次建议控制在 3 层以内，不应超过 5 层。
- `switch` 分支原则上不要从一个 `case` 贯穿到下一个 `case`；如确需 fallthrough，必须在两个 `case` 之间写清原因。
- 能提前返回时优先提前 `return`，以降低缩进层级。
- 保持逻辑块简单，避免巨型类和巨型源文件。
- 源文件建议控制在 2000 行以内。

## 变量、结构与类

- 变量声明应尽可能局部化，缩小作用域。
- C++ 禁止在函数开头集中定义全部局部变量；变量应靠近首次使用处定义。
- 变量定义时必须初始化。
- 严禁滥用全局变量和静态变量。
- 公共变量会增大模块耦合，应尽量减少。

## 函数设计

- 必须检查所有函数参数输入的有效性。
- 必须检查函数使用的非参数输入，例如数据文件、公共变量、全局状态等。
- 避免参数过多；未使用参数必须从接口中移除。
- 非调度函数应减少或避免控制参数，尽量只使用数据参数。
- 函数规模建议控制在 50 行以内，不应超过 200 行。
- 一个函数只完成一件功能。
- 不要设计多用途、面面俱到的函数。
- 可以为简单功能编写小函数，以增强语义、可读性、可维护性和可测试性。
- 避免把没有关联或关联很弱的语句放入同一个函数。
- 多段代码重复做同一件事时，应检查函数划分是否合理；若重复代码完成同一功能，可抽取函数。
- 设计高扇入、合理扇出的函数；普通函数扇出建议 3 到 5，不应大于 7。
- 积极使用 `const`：
  - 不应修改的入参使用 `const`。
  - 不修改对象状态的成员函数声明为 `const`。
  - 倾向使用常量而不是可变变量。
  - 尽量不要使用 `const_cast` 破坏常量性。

## 错误处理与断言

- 错误值返回应使用 `int` 或项目统一错误码，不使用异常。
- 禁止使用 C++ 异常作为项目错误处理机制。
- 工程内部所有错误定义必须统一管理。
- 函数返回值必须清楚、明确，让调用者不容易忽视错误情况。
- 断言表达式只能做条件判断，不能改变程序状态。
- 禁止在断言中调用会产生副作用的函数，例如 `assert(init())`。
- 断言不能用于已知可能发生的运行时错误，如文件不存在、读写失败、函数执行失败等。
- 可预期错误应通过错误码和日志处理。
- 断言仅用于检查程序逻辑正确性和数据一致性。

## 宏定义

- 宏表达式必须使用完备括号。
- 宏参数在展开时必须加括号，例如 `((a) * (b))`。
- 调用宏时，实参不允许带有自增、自减、赋值等副作用。
- 能使用 `const`、`constexpr`、`inline` 函数或枚举替代宏时，优先避免宏。

## 日志规范

- C++ 项目优先使用 `kiran-log`，C 项目建议使用 `zlog`。
- 日志级别从低到高为 `DEBUG`、`INFO`、`WARNING`、`ERROR`、`FATAL`。
- 日志信息必须完整描述一件事情，不能只打印状态变量。
- 日志应在没有源码上下文时仍能说明发生了什么、关键对象是什么、失败原因是什么。
- 可预期错误不应使用断言，应输出告警或错误日志。
- 自定义 `zlog` 配置时，必须基于默认配置添加规则，不得破坏原有规则。

## Agent 执行检查清单

AI Agent 在提交 C/C++ 代码变更前必须自查：

- 是否遵循项目现有 `.clang-format` / `cmake-format`。
- 是否使用 4 空格缩进且无 Tab。
- 是否所有控制语句执行体都有 `{}`。
- 是否命名与 C、GTK C++、QT C++ 的目标规范一致。
- 是否删除无用代码、魔术数和无意义命名。
- 是否新增或修改对外接口注释。
- 是否变量靠近使用处定义并已初始化。
- 是否函数参数和外部输入都做了有效性检查。
- 是否没有引入异常处理机制。
- 是否错误码、返回值和日志足够清楚。
- 是否断言无副作用，且未用于可预期运行时错误。
- 是否宏有完整括号且调用宏的参数无副作用。
- 是否没有留下 `add by`、`modify by` 等手工变更历史。
- 是否构建配置、共享库版本、`.pc` 文件等发布相关内容符合项目要求。
